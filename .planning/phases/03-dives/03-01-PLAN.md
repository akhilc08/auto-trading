<objective>
Establish the shared foundation every Phase 3 Dive depends on: the `dives/` directory, a single
conventions reference (`dives/_conventions.tsx`) that fixes the hard rules the four Dives must obey
(data-is-rows guard, fully-qualified double-quoted table names, the `N()` BigInt helper, the
green/red hex constants, the empty-state pattern, and the SQL-injection-safe strategy allow-list),
and a `dives/README.md` documenting the deliverable model (every Dive is BOTH a versioned `.tsx`
file AND a live Dive created via the MotherDuck MCP tool). This plan also runs the Wave 0 validation
gate: confirm the MotherDuck MCP tools are reachable and the SQL pre-flight block resolves all four
tables against the live `trading` DB.

This is the one plan that produces shared artifacts; the four Dive plans (02–05) run in parallel in
Wave 2 and each reads from these conventions. Per DIVES-01..04 the conventions cover all four Dives,
so all four requirement IDs are carried here and re-asserted in their dedicated plans.

Purpose: Fix the cross-cutting rules ONCE so the four parallel Dive authors cannot diverge on table
names, colors, BigInt handling, empty-state, or the injection-safe filter.
Output: `dives/_conventions.tsx`, `dives/README.md`, and a confirmed-green SQL pre-flight + MCP reachability check.
</objective>

<deliverable_model_note>
Dives are React TSX components with embedded SQL, authored and deployed via the MotherDuck MCP tools
(`create_dive` / `save_dive` / `edit_dive_content`) — NOT via a local dev server or build step. There
is no npm install: `react`, `recharts`, `lucide-react`, and `@motherduck/react-sql-query` are bundled
by the MotherDuck Dive runtime (03-RESEARCH.md "Available Dive Runtime Libraries"). For reviewability
and version control, each Dive's TSX source is ALSO committed as a `dives/*.tsx` file in this repo.

as a Dive itself.

<strategy_allowlist_note>

`useDiveState` value — 03-RESEARCH.md Pitfall 6, T-3-01). Mitigation: the filter value MUST come from a
hardcoded closed allow-list, never raw user input. The source of truth for which strategies actually run
and log to `trades` is `core/accounts.py` `_ACCOUNT_STRATEGIES`. As of this writing that file registers

Note the discrepancy: 03-RESEARCH.md says "13 known strategies" and EXEC-03 lists rl_alpha/deep_learning/
alt_data_fusion (those exist as `strategies/` directories but are NOT in `_ACCOUNT_STRATEGIES`, so they do
not currently log trades). Derive `STRATEGIES` from `core/accounts.py` as the authoritative live set — read
it during the task, do not hardcode from this note in case the file changed. Do NOT modify `core/accounts.py`
or any strategy file (project rule + INTEG-06 spirit).

|----------|-------------|
| Browser (useDiveState URL value) → SQL | The strategy filter value (DIVES-01) is user/URL controlled and crosses into the SQL string |
| MotherDuck MCP → trading DB | Read-only queries over the user's own database |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Tampering (Injection) | DIVES-01 strategy filter (useDiveState value interpolated into SQL) | mitigate | This foundation plan defines the closed `STRATEGIES` allow-list (mirror of core/accounts.py); DIVES-01's filter value must be one of `STRATEGIES` or `all`, never raw user input interpolated into SQL (03-RESEARCH.md Pitfall 6) |
| T-3-02 | Information Disclosure | Read queries over trading DB | accept | Read-only SELECTs over the user's own MotherDuck DB; no PII, no cross-tenant data; LOW risk |
| T-3-03 | Denial of Service | Unbounded SELECT on trades | mitigate | Conventions require DIVES-01 to keep the `LIMIT 500` from the research SQL; documented in README |
</threat_model>
